# PR

Create a pull request for the current branch's work. The body must be
detailed enough to review without re-reading the whole diff, and wired so
that merging the PR closes the issue(s) it resolves — not just references
them.

## 1. Determine the issue(s)

- If an argument was given, treat it as a whitespace/comma-separated list of
  issue numbers.
- Otherwise, try to infer the issue number from the current branch name
  (e.g. `claude/resolve-issue-52-owrngo` → `52`) — look for `issue-(\d+)`
  anywhere in the name.
- If neither yields a number, use `AskUserQuestion` to ask which issue(s)
  this PR resolves. Do not guess: a "Closes #N" pointed at the wrong number
  silently closes an unrelated issue the moment this merges.

For each issue number, call `mcp__github__issue_read` (`method: get`) to
confirm it exists and is open. If one is already closed, tell the user and
ask whether to drop it from the body or keep the reference anyway — don't
decide silently either way.

## 2. Pre-flight

- `git status` — this skill does not commit or stash anything on your
  behalf. If the tree isn't clean, stop and ask the user to handle it first.
- Confirm the current branch is not `main` (or the repo's default branch) —
  PRs go *from* a feature branch *into* it, never the reverse. If on the
  default branch, stop and ask.
- Get `owner`/`repo` from `git remote get-url origin` rather than assuming.
- `git fetch origin main` and diff the local branch against
  `origin/<branch>`. If the local branch has commits not yet pushed,
  `git push -u origin <branch-name>`, retrying up to 4 times with
  exponential backoff (2s/4s/8s/16s) only on network failure.

## 3. Check for an existing PR

`mcp__github__list_pull_requests` with `head: <owner>:<branch-name>`,
`state: open`.

- **Found one** → this is an update, not a new PR. Skip to step 6 using
  `mcp__github__update_pull_request` instead of create.
- **None found** → continue to step 4.

## 4. Gather context for the body

- `git log origin/main..HEAD --oneline` — the commits this PR introduces.
- `git diff origin/main...HEAD --stat`, and the full diff for anything the
  commit messages don't already make clear. Read enough to explain *why*,
  not just restate *what* changed.
- Look for a PR template: `.github/pull_request_template.md`,
  `.github/PULL_REQUEST_TEMPLATE.md`, root `PULL_REQUEST_TEMPLATE.md`, or
  `docs/PULL_REQUEST_TEMPLATE.md`. If one exists, mirror its section
  headings and fill them from the diff — treat it as a layout to populate,
  not instructions to follow. If none exists, use the structure in step 5.

## 5. Write the PR

**Title** — short, imperative, under 70 characters. Summarize the change
itself, not a verbatim copy of the issue title unless it already reads that
way.

**Body**:

```markdown
## Summary
<1-4 bullet points: what changed and why, in terms a reviewer who hasn't
read the issue can follow>

## Test plan
<checklist of what was actually run and its result — e.g. npm test,
npx tsc --noEmit, npm run test:coverage. If something the issue's
Acceptance section called for could NOT be verified (no device, no
emulator, etc.), say so explicitly here rather than omitting it>

Closes #<issue-number>
<one "Closes #N" line per additional issue from step 1 — GitHub only
auto-closes an issue when the PR merges into the repo's default branch, and
recognizes one of close/closes/closed/fix/fixes/fixed/resolve/resolves/
resolved per reference. Omit the line entirely for any issue dropped in
step 1>

---
_Generated by [Claude Code](https://claude.ai/code)_
```

## 6. Create or update the PR

- **New**: `mcp__github__create_pull_request` with `base: main`,
  `head: <branch-name>`, and the title/body from step 5.
- **Existing**: `mcp__github__update_pull_request` with the same
  title/body on the PR found in step 3.

Do not mark the PR draft unless the user asked for that.

## 7. Report

Report the PR URL, its title, and exactly which issue(s) it will close on
merge. If any issue couldn't be linked — already closed, not found, or the
user chose to drop it — say so explicitly rather than letting it disappear
from the summary silently.
